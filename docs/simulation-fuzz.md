# Simulation fuzzing

`tools/Test-SimulationFuzz.ps1` implements specification §20.5 independently of the existing ten-minute loader fuzz test. The default suite alternates 16 Mossy Hollow cases with 16 generated maps. Every case advances 10,000 actual simulation ticks in two fresh runs and compares the canonical hash and session state after every tick. A terminal mission starts a recorded deterministic epoch; calls that do not advance a tick cannot count toward the requirement.

```powershell
./tools/Test-SimulationFuzz.ps1
./tools/Test-SimulationFuzz.ps1 -Seed 20261027 -EvidenceDirectory artifacts/simulation-fuzz/my-new-run
# CLI equivalent, with the pinned .NET SDK active:
dotnet src/Dungeons.Tools/bin/Release/net8.0/Dungeons.Tools.dll sim-fuzz game/levels/mossy_hollow/level.json artifacts/simulation-fuzz/new-run 32 10000 23443019308292698
```

The generator is versioned. It uses an independent seeded input RNG and map RNG, 8/16/32/64-square maps, one through four player slots, randomized walls, nonwalkable water, raised cells, stairs, weighted floor and open map edges. It instantiates actual registry heroes, zombies, skeletons and all three pickup families. Segments of 1–24 ticks exercise movement, aiming, attack, ranged, roll, potion and interact, including the public input constructor's nonfinite sanitization. Pressed flags contain only new held edges. The nightly job records a different UTC-date seed; any failure can be rerun using the stored suite seed and case count.

Protocol **2** replaces three generated cases in the default 32-case suite with validated, canonically serialized random gate maps. An interactable open gate initially shares a cell with food; full hero health keeps that collectible live while random Interact edges close the gate. These maps also exercise bow shots and normal gate collision. Exact `level.json` bytes must match each case's recorded source hash. Every gate case must actually close a gate during its 10,000 ticks; suites without that coverage are labelled diagnostic even if their tick counts are sufficient. The original generated-map/player-size coverage remains, and no runtime-only API or reflection is used to manipulate Core.

The oracle checks finite current/previous transforms, facing and velocities; every active entity centre in bounds; nonnegative living HP; and circle-versus-cell penetration at the specified **0.001 m** limit. Living actors and pickups may not overlap solid terrain or the map boundary. Projectiles use their actual height and projectile-blocking flags. Static objects can own blocking terrain (closed gates), decorative markers do not collide, and dead bodies cease collision participation; those semantic distinctions are explicit in the oracle rather than exceptions for particular seeds. Circle overlap is measured independently with nearest-point geometry, without calling Core's collision resolver.

Outputs must be new. The runner publishes isolated Core/Tools binaries and copies the content registry before running. It retains exact authored level bytes, content/Core/Tools identities, every generated baked cell and placement, the entire sanitized input stream in run-length form, terminal epoch seeds, final hashes and actual tick/entity counts. A case failure adds its run, step, tick, entity/rule, state hashes and all entity transforms as IEEE float bits, and propagates a nonzero process exit. Invalid arguments and existing evidence are rejected without overwriting files. A short diagnostic run is labelled `simulationFuzzAcceptance=false`. Neither a fast simulation run nor nightly workflow configuration constitutes a two-hour soak, physical acceptance or a hosted CI pass.

To reproduce against the archived binary/content rather than a later checkout, run `dotnet <evidence>/bin/Dungeons.Tools.dll sim-fuzz <evidence>/cases/source.json <new-output> <cases> <ticks> <suiteSeed> --content <evidence>/content`, using the parameters in `result.json`. Four real CLI rejection contracts and a short-run acceptance contract run after every published suite. Publishing keeps the ordinary apphost enabled so later `dotnet run --no-build` gates retain their executable; isolation comes from the separate publish directory.

### Dynamic gate-volume follow-up

The later gate audit found an additional real failure: closing a gate moved actors but left collectibles embedded in the new solid cells. The focused pre-fix test reports 0.2 m penetration (`artifacts/hardening/gate-volume/before.log`). A differential run pairs the new protocol-2 Tools binary with the exact old shipped Core DLL from the first desktop soak package. That run fails case 9 at tick 11 for `core:food` inside cell (2,1); the complete map/inputs/failure are retained under `pre-fix-counterfactual/`. This is actual regression detection, not a synthetic expected-error record.

Closing now plans safe collectible positions in the same transaction as actors. A pickup that cannot fit causes a complete rollback. After safe displacement commits, shots whose circles overlap the closing gate are expired immediately and emit one terrain-hit event with the correct blocked cell; misses/tangencies survive and rollback leaves shots untouched. Functional geometry/rollback tests and a 200-transition zero-allocation check pass.
