# Desktop soak validation

Specification §21 M8 requires a crash-free two-hour soak on each platform. `tools/Test-DesktopSoak.ps1` runs an exported Windows package in one native game process for a requested wall-clock duration (7,200 seconds by default). It copies the executable and complete .NET payload to a new evidence directory, hashes every file and checks the loaded Game/Core module IDs against their PE metadata. Subsequent source edits, builds, exports and replay regeneration cannot change that private package or its archived input streams. Evidence may not be nested inside the source payload, and files added/removed/changed during the run invalidate the result.

```powershell
# Prepare the current desktop package (automated smoke uses Dummy audio):
./tools/Export-M0.ps1 -Platform Windows -SmokeTest -Rendered
# Real two-hour desktop run, on the native Mobile/Vulkan renderer:
./tools/Start-ValidationJob.ps1 -EvidenceDirectory artifacts/soak/my-new-two-hour-run
# Durable supervisor status and console transcript:
Get-Content artifacts/soak/my-new-two-hour-run.launch/result.json
# Short accelerated diagnostics, never two-hour acceptance:
./tools/Test-DesktopSoak.ps1 -Seconds 10 -Fast -Renderer gl_compatibility
./tools/Test-DesktopSoakContracts.ps1
```

The desktop-only scene `game/editor/soak.tscn` embeds the actual `AppRoot` in an isolated profile folder. It alternates the development full-clear, ambush and death/respawn replays, requiring exact tick counts/final hashes, genuine full-clear result controls and an actual respawn. It drives the normal catalogue controls and starts an ordinary recorded attempt after every full clear. That attempt pauses/resumes, returns to the catalogue and closes through the production store. The harness verifies the persisted profile attempt count, matches the saved replay's tick/hash, plays the archive through Core, and preserves a copy outside the normal five-replay retention folder. Existing player profiles/settings and reviewed goldens are not used. Hardware haptics are disabled for this QA scene. Audio routing/decoding runs on the Dummy driver; this is not listening acceptance.

Ordinary runs use real frame deltas and the production fixed-step host. Accelerated mode explicitly drives the same host multiple times per rendered frame and is marked diagnostic. The acceptance policy requires an actual duration of at least 7,200 seconds, at least 54 simulated ticks and 15 drawn frames per elapsed second averaged over the entire run, no ten-second frame-loop gap, a native renderer, every required flow and no acceleration. The external supervisor additionally verifies its own wall-clock duration, process identity, zero exit, final marker, runtime module identity and unchanged package. Native error/script-error and shutdown leak diagnostics fail the run. A 45-second stale heartbeat, process death or duration plus ten-minute overrun is a failure, with the partial telemetry/logs preserved. The process completes its current cycle before stopping, so successful elapsed time may exceed the requested duration.

`heartbeat.json` and `samples.jsonl` record actual elapsed time/ticks/drawn frames, current flow, replay/normal-attempt counts, RSS, managed memory, native nodes/resources/orphans and texture bytes every five seconds. `process.json` records PID, creation time and the private executable. `package-files.json` seals executable/payload hashes. The final outer `result.json` is authoritative: a scene's own positive marker alone is insufficient. Telemetry supports memory-growth review; a passing crash-free soak does not separately approve all performance, battery or thermal budgets.

During unattended QA, the supervisor holds a temporary, thread-scoped display/system idle request using [Microsoft's documented SetThreadExecutionState API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate). It restores the previous state in `finally`; process/thread exit also ends its request. It does not change a power plan or enable away mode. Explicit user sleep/lock remains possible and a resulting stall can invalidate the run.
